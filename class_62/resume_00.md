Imaginemos una inteligencia artificial que no se limita a responder una pregunta y detenerse, sino que conserva información entre pasos, realiza acciones y puede continuar su trabajo después de una interrupción. Para entender cómo se construye un sistema así, conviene empezar por distinguir una llamada aislada a un modelo de un agente. En una llamada aislada, una persona hace una pregunta y el modelo produce una respuesta; el sistema no necesariamente conserva estado, utiliza herramientas ni mantiene un proceso de control. En un agente, en cambio, el modelo forma parte de un sistema más amplio. El modelo procesa la entrada y puede señalar qué acción considera apropiada, pero el sistema que lo rodea conserva el estado, ejecuta las acciones y controla el flujo hasta que la tarea termina.

Podemos describir ese sistema mediante varios componentes que colaboran. El primero es el modelo de lenguaje, que toma decisiones sobre el siguiente paso a partir de la información que recibe. El segundo es el estado, es decir, la información que el agente lleva consigo entre pasos y que le permite mantener el contexto necesario. El estado debe ser explícito y contener lo que el paso siguiente necesita; guardar información sin límites puede degradar el rendimiento y aumentar los costos. El tercer componente son las herramientas: funciones externas que permiten realizar tareas o consultar información fuera de los datos de entrenamiento del modelo. Una herramienta debe tener entradas y salidas definidas y una responsabilidad clara. También es importante pensar en los reintentos, para que repetir una llamada no produzca efectos secundarios duplicados, y en límites de tiempo para que una operación no detenga indefinidamente el resto del agente. El cuarto componente es el bucle de control, que organiza la comunicación entre el modelo, el estado y las herramientas.

Pensemos en una consulta sobre el clima en Madrid. El estado podría mantener la ubicación y un valor de temperatura que todavía no se ha completado. Un paso del sistema puede pedir al modelo que decida qué hacer; otro puede ejecutar una herramienta del clima. La estructura que organiza estos pasos puede representarse como un grafo. En ese grafo, los nodos son unidades de trabajo y cada nodo debería tener una responsabilidad clara. Las aristas son conexiones dirigidas que expresan a qué paso se avanza. Algunas aristas pueden ser condicionales: por ejemplo, después de recibir una respuesta del modelo, el sistema puede comprobar si hay una solicitud de herramienta y elegir el nodo de herramientas, o terminar si el modelo ya produjo una respuesta final. Antes de ejecutar un grafo, se compila para validar su estructura, como los nodos, las aristas y el punto de entrada.

Ahora sigamos una ejecución completa del bucle agentico. Primero, el sistema envía al modelo el historial de la conversación junto con el prompt del sistema. El modelo devuelve una respuesta que puede incluir texto y una señal estructurada de que quiere usar una herramienta. En vez de intentar descubrir esa intención buscando palabras en texto libre, el sistema puede comprobar los campos estructurados de la respuesta. En el material se muestra que, para Anthropic, se puede comprobar si el motivo de parada es «tool_use» y si la respuesta contiene un bloque de tipo «tool_use». Para OpenAI se mencionan «finish_reason» con «function_call». Cuando se detecta una llamada, el sistema extrae el nombre de la herramienta y sus parámetros, ejecuta la función correspondiente y vuelve a insertar el resultado en el historial, asociado con la llamada original. A continuación, el historial actualizado vuelve al modelo. El ciclo continúa mientras el modelo solicite herramientas; cuando no se detecta otra llamada, el texto se considera la respuesta final y el bucle termina.

La regla importante es que el modelo no ejecuta directamente la herramienta ni controla por sí mismo el flujo del programa. El modelo señala la acción; el sistema interpreta la señal, ejecuta la función y decide qué hacer después. El resultado de la herramienta tiene que volver al historial con el formato esperado para que el modelo pueda relacionarlo con su solicitud. Así se evita depender de interpretar texto ambiguo y se mantiene claro quién toma cada responsabilidad.

La forma más sencilla de desarrollar un agente es avanzar por capas. Primero se comprueba que una herramienta funcione por sí sola con una entrada fija y que se comprende su esquema. Ese esquema puede describir el nombre de la herramienta, lo que hace y un esquema de entrada que indique los parámetros esperados. El ejemplo del material define una herramienta llamada «get_weather», que obtiene el clima actual de una ciudad y recibe un parámetro «city» de tipo texto. Una vez comprobada la herramienta, se presenta su definición al modelo para que este pueda decidir si la necesita en una interacción de un solo turno. Después se añade un bucle de varios turnos para que el sistema pueda ejecutar una herramienta, devolver el resultado al modelo y continuar mientras la tarea siga sin resolverse. Comprobar cada etapa antes de añadir la siguiente permite aislar problemas antes de que el sistema tenga más complejidad.

Cuando el agente debe utilizar varias herramientas, una opción descrita en el material es mantener un registro que asocie el nombre de cada herramienta con su función. Así, en vez de ampliar una cadena de condiciones cada vez que se añade una nueva herramienta, el sistema puede despachar la llamada usando el nombre recibido y los parámetros correspondientes. Por ejemplo, el registro puede asociar «get_weather» con la función del clima y «get_news» con la función de noticias. Si la ejecución de una herramienta falla por un problema de red, una entrada inválida u otro error inesperado, el sistema puede capturar la excepción y devolver un mensaje estructurado y claro como resultado de la herramienta. El material recomienda no exponer al modelo rastros de excepción crudos, sino permitir que reciba un mensaje de error comprensible y decida cómo proceder, por ejemplo, reintentando, utilizando una alternativa o respondiendo. También hay que definir condiciones de parada. Un límite máximo de iteraciones evita que el agente se ejecute indefinidamente si continúa solicitando herramientas sin llegar a una respuesta final; el ejemplo del material utiliza diez iteraciones como límite ilustrativo.

Un bucle programado directamente puede servir como punto de partida, pero a medida que crece resulta más difícil de extender. La lógica de ejecución y la de enrutamiento pueden mezclarse, el estado puede quedar implícito en el historial y en las condiciones del programa, y una caída puede hacer que se pierda el progreso. Estas limitaciones preparan el terreno para entender qué aporta LangGraph: convertir el flujo del agente en una estructura explícita de nodos y aristas, con un estado definido y puntos de control que ayudan a recuperarse de interrupciones.

En el ejemplo de LangGraph, el estado se define con un «TypedDict» que contiene una lista de mensajes. El tipo «Annotated», junto con el reductor «add_messages», indica cómo acumular las actualizaciones de mensajes y mantener consistente el historial mientras el agente avanza. Cada nodo recibe el estado actual y devuelve una actualización. El nodo «call_model» vincula las herramientas al modelo, lo invoca con los mensajes actuales y devuelve la respuesta como un nuevo mensaje del estado. Para ejecutar las llamadas a herramientas se utiliza «ToolNode», que recibe la lista de herramientas y se ocupa de ejecutar las que el modelo haya solicitado. En estos fragmentos, «llm» y «tools» se dan por existentes; el contenido de la clase no especifica cómo configurarlos ni proporciona los comandos de instalación o credenciales necesarios para convertir el ejemplo en un programa autónomo.

Después se crea un «StateGraph» a partir del esquema del estado y se registran los nodos del agente y de las herramientas. Una arista conecta el punto de inicio con el nodo del agente. La función de enrutamiento «should_continue» consulta el último mensaje del estado y comprueba si contiene llamadas a herramientas. Si las contiene, la ruta se dirige al nodo «tools»; si no, se dirige al final. Después de ejecutar las herramientas, otra arista vuelve al agente para que el modelo pueda incorporar los resultados y decidir qué hacer a continuación. Cuando el flujo está definido, «graph.compile()» valida la estructura antes de la ejecución. Después, «app.invoke(initial_state)» ejecuta el grafo con un estado inicial que puede contener un mensaje de usuario como «¿Cuál es el clima en Madrid?». El resultado es el estado final después de recorrer los nodos; el material no fija un texto concreto de respuesta.

La fiabilidad de un agente también depende de cómo responde a las interrupciones y de cómo permite revisar su comportamiento. Si el agente encuentra una ambigüedad que no debería resolver adivinando, puede pausar, guardar el estado actual, pedir una aclaración humana y reanudar el trabajo incorporando la respuesta. Este patrón se conoce como humano en el bucle. También se puede transmitir información parcial mientras el agente continúa trabajando. Los puntos de control permiten conservar el progreso para recuperarse de fallos o reinicios; en el ejemplo de LangGraph se muestra la compilación con «InMemorySaver» para añadir checkpointing en memoria. Esa mención ilustra el mecanismo, pero no especifica una configuración de persistencia externa.

Para comprender por qué un agente tomó una decisión, se pueden utilizar rastreos que registren las entradas y salidas de los nodos, las llamadas a herramientas y sus resultados, las instantáneas del estado, las transiciones y la información de tiempo. Un rastreo permite revisar el recorrido en lugar de intentar deducirlo a partir de la respuesta final. Las evaluaciones, por su parte, son comprobaciones automatizadas para determinar si el comportamiento fue correcto ante una entrada. Juntos, los rastreos y las evaluaciones ayudan a observar el comportamiento y a identificar oportunidades de mejora.

Al terminar, volvamos a la idea central. Un agente no es solamente un modelo que recibe una pregunta y devuelve texto. Es un sistema en el que el modelo propone acciones, el estado conserva la información necesaria, las herramientas realizan tareas concretas y el bucle o grafo controla las transiciones y la condición de finalización. Las herramientas necesitan contratos claros; el sistema debe manejar errores y detener ciclos que se prolongan; y los puntos de control, las interrupciones y los rastreos ayudan a recuperar y entender el proceso. LangGraph hace explícita esa arquitectura mediante un estado, nodos, aristas, compilación e invocación. De esa manera, el foco pasa de una llamada aislada a un flujo de trabajo que puede utilizar herramientas, conservar contexto y mostrar con mayor claridad cómo avanza desde la entrada hasta la respuesta final.
